Pipelines

From a sentence to a running job

"Sync MySQL users to StarRocks" becomes a validated HOCON config. The agent tests connectivity first, runs the job, parses metrics, and when something breaks, it diagnoses the log and fixes the config itself.

generate

NL → HOCON config

12 built-in templates (MySQL-CDC, Kafka, StarRocks, ClickHouse…) and documented parameters for 19 connectors keep the agent from hallucinating options.

run

Auto-diagnose & retry

On failure the agent reads the SeaTunnel log, clusters the root cause, patches the config, and reruns — structured metrics on every pass.

track

Versioned configs

Every write is a timestamped version. Browse history, diff any two versions, restore or delete safely, and compare changes in the UI.

Governance

Safety nets on every query

A deterministic toolchain that never needs a database connection: paste SQL in chat, or gate it in CI.

review

SQL Code Review

Deterministic linter + LLM semantic pass over 15 checks — GROUP BY completeness, cartesian joins, partition filters — with SARIF output for GitHub Code Scanning.

lineage

Impact & drift

SQL diff × lineage reports the release blast radius; schema drift grades every DDL change breaking / risk / info. Both gate CI with --fail-on.

protect

PII propagation scan

Sensitive columns traced downstream through column-level lineage — unmasked copies escalate severity; md5/mask chains count as masked.

quality

DQC gates

YAML rules compiled to deterministic aggregates: row counts, null rates, uniqueness, enum domains — with run-history baselines and Feishu alerts.

translate

Dialect transpile

Hive ⇄ Spark ⇄ Doris ⇄ StarRocks with a structured incompatibility report. The SQL is never executed.

advise

Governance advisor

Lineage × query audit logs surface decommission candidates, hot tables and partition-filter offenders — recommendations only, never touches a table.

How it works

One loop: generate, run, diagnose, fix

Every pipeline request moves through the same closed loop. The agent never guesses twice at the same failure — logs are clustered by root cause, and each fix is a versioned config diff you can inspect.

01 · understand

Understand

Schema-aware matching — keyword + CJK n-gram scoring over table names, columns and Chinese comments; partition suffixes (_di/_df/_hf) classified automatically.

02 · generate

Generate

HOCON config from templates and documented connector parameters, or deterministic SQL from the metric semantic layer. Connectivity tested first.

03 · execute

Execute

Job output parsed into structured metrics: rows read/written, bytes, duration, status. Every query logged as JSONL.

04 · repair

Repair

On failure: read the log, cluster the exception by root cause, patch the config, retry. Every fix is a versioned diff.

Trust, measured

Benchmarked, gated, reproducible

Accuracy is not a vibe here. Retrieval, SQL generation and review quality each have their own regression gate, runnable in CI.

t2s-bench

Retrieval gate

A 56-question benchmark over table and metric retrieval; --gate fails the build when recall regresses.

t2s-eval

End-to-end accuracy

Question → agent → result set, compared against golden SQL. Multi-model comparable, so you can swap LLMs and see what actually changes.

metrics validate

Caliber CI gate

The semantic layer is linted like code: broken metric definitions fail CI before anyone gets a wrong number.
