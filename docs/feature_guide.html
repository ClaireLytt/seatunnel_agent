CORE ReAct Agent Loop

The agent follows a Reason → Act → Observe loop. Each iteration, the LLM reasons about the task, selects a tool, executes it, and observes the result — up to 20 iterations per task, with automatic retry tracking.

User Task → THINK → ACT (tool call) → OBSERVE (result) → Answer

Entry Points

MethodDescriptionSystem Prompt Hint
agent.run(task)Natural language task, fresh conversationrun — suggests templates, connection tests
agent.chat(msg)Continue multi-turn conversationrun — preserves message history
agent.run_with_config(path)Run a specific config, auto-fix on failurerun_config — targets existing file
agent.validate_only(path)Validate config without runningvalidate — blocks job execution
agent.diagnose_log(path)Analyze log file for root causediagnose — focus on errors

Retry & Safety Limits

When run_seatunnel_job fails, the retry counter increments. After max_retries (default 3) consecutive failures, the agent is forced to stop and summarize what it tried. A successful run resets the counter. The loop itself caps at 20 iterations.

Path Traversal Protection

write_config and use_template resolve the target path and verify it stays within the current working directory using Path.resolve().is_relative_to(cwd). Any attempt to write outside (e.g., ../../../etc/evil.conf) returns an error instead of writing.

resolved = Path(config_path).resolve()
cwd = Path.cwd().resolve()
if not resolved.is_relative_to(cwd):
    return {"error": "Path is outside the working directory"}

Template Rendering

Templates use Python's string.Template with ${placeholder} syntax. The render_template(name, params) function merges user-provided values with defaults, so only overrides are required.

# Template parameters are merged with defaults
merged = {p["name"]: p["default"] for p in template.parameters}
merged.update(user_params)
# safe_substitute leaves unknown placeholders as-is
return Template(content).safe_substitute(merged)

F2 Connection Testing

TCP connectivity probe for databases, Kafka, and other services. The agent tests connections before generating configs to avoid write-run-fail-fix cycles.

How It Works

socket.create_connection((host, port), timeout=5) tests raw TCP reachability. The result includes latency in milliseconds and an optional service type label.

# Tool input
{"host": "mysql-prod.internal", "port": 3306, "service_type": "MySQL"}

# Success response
{"reachable": true, "latency_ms": 4.2,
 "message": "MySQL at mysql-prod.internal:3306 is reachable (4.2ms)"}

# Failure response
{"reachable": false,
 "message": "Cannot reach mysql-prod.internal:3306 — Connection refused"}

UI Display

Connection results render with semantic badges: ✅ Reachable or ❌ Unreachable, making success/failure visible at a glance without reading JSON.

F3 Session Context Memory

The agent tracks what it has done in the current session: configs created, validation results, connection tests, and job outcomes. This context is injected into every LLM call so the agent can resolve references like "run the config again" or "fix that error".

Tracked State

  • last_config_path — most recently written or read config file path
  • created_configs — all config files written this session (no duplicates)
  • validated_configs — all config files that passed validation
  • last_job_success — whether the last job run succeeded
  • last_job_error — truncated error from the last failed run
  • last_connection_test — most recent host:port test result
  • last_template_lookup — whether templates were listed

Context Injection

_build_context_hint() always produces a ## Session Context block appended to the system prompt — even when the session is empty (showing "No config files have been created or read yet"). This section includes an explicit instruction: "Do NOT guess file paths — only use paths listed here or ask the user."

Persistence

Context is saved alongside chat history in Session.agent_context. When the user loads a previous session from the history dropdown, the agent's context dict is restored so it can continue intelligently. The field defaults to {} for backward compatibility with sessions saved before this feature.

F4 Configuration Diff Display

When the agent overwrites an existing config, the diff between old and new content is computed and displayed, so the user can see exactly what changed.

Implementation

write_config reads the old file before overwriting. If content differs, difflib.unified_diff() produces a diff included in the JSON response alongside "had_changes": true. When content is identical, "had_changes": false is returned with no diff. New files return neither field.

# Response when overwriting with changes
{"success": true, "had_changes": true,
 "diff": "--- job.conf.bak\n+++ job.conf\n@@ -1,2 +1,2 @@\n-rows = 10\n+rows = 100"}

# Response when content is identical
{"success": true, "had_changes": false}

# Response for new file
{"success": true}

UI Rendering

The chat formats diff output as a fenced ```diff code block (truncated to 800 characters). When had_changes is false, the result shows "Success (no changes)" to prevent confusion.

The UI shows what the agent is doing at each moment: which reasoning step it's on, what tool it's calling, and the streaming text response.

Streaming Text Buffer

text_delta events accumulate in a buffer. The buffer is flushed to a chat message with a blinking cursor (▌) when a non-delta event arrives. A text event clears the buffer entirely — it represents the complete response and replaces any partial deltas.

Step Display

Step numbers show without a denominator (e.g., "Step 3" not "Step 3/20") to avoid implying the agent will use all 20 iterations. Phase labels translate internal states: thinking → "Thinking...", executing_tools → "Executing tools...".

F6 Event-driven Streaming

The UI refreshes immediately when new events arrive, replacing the original 300ms polling interval with a threading.Event signal.

EventCollector

Thread-safe event buffer with a signaling mechanism. The agent thread calls on_event() to append events and signal the UI thread; the UI thread calls wait_for_event(timeout=0.3) which returns immediately when signaled or after the timeout.

class EventCollector:
    def __init__(self):
        self.events = []
        self.lock = threading.Lock()
        self.done = False
        self._new_event = threading.Event()     # signal

    def on_event(self, event_type, data):
        with self.lock:
            self.events.append({"type": event_type, **data})
            if event_type == "final_answer":
                self.done = True
        self._new_event.set()                   # wake UI thread

    def wait_for_event(self, timeout=0.3):
        self._new_event.wait(timeout)           # block until signal or timeout
        self._new_event.clear()

Why Not Polling

The original time.sleep(0.3) loop introduced up to 300ms latency on every event. With threading.Event, the UI wakes within microseconds of a new event. The 0.3s timeout remains as a fallback — if no event arrives, the loop still checks collector.done to avoid hanging.

F7 Stop Control

Users can interrupt a running agent mid-task. The stop button injects a final_answer event into the collector, causing the streaming loop to exit gracefully.

Mechanism

The collector_holder dict gives the stop button access to the active EventCollector. Clicking the stop button calls collector.on_event("final_answer", ...), which sets done = True and signals the UI thread. The agent's background thread continues running (daemon thread) but no further output is displayed.

def _handle_stop(lang):
    c = collector_holder.get("current")
    if c and not c.done:
        c.on_event("final_answer", {"text": _t(lang, "stopped")})
    return show_send_btn, hide_stop_btn

UI Behavior

When a task starts, the Send button hides and the Stop button [■] appears. On stop or completion, they swap back. The stopped message is localized: "Agent stopped by user." (EN) / "已被用户中断。" (ZH).

TextMessage Normalization

Before export, _normalize_chat() processes the chat history to unwrap Gradio's ChatMessage objects and strip {'text': '...', 'type': 'text'} wrappers that appear in some Gradio versions. This uses ast.literal_eval for safe parsing and recurses to handle double-wrapped values.

F10 Bilingual Interface (EN/ZH)

Every UI label, placeholder, and status message supports English and Chinese. The language dropdown in the top bar switches all text dynamically without page reload.

Architecture

The _I18N dict maps language codes to key-value pairs. The _t(lang, key) helper looks up the key in the current language, falling back to English. When the language changes, _switch_lang() returns gr.update() calls for all 11 language-sensitive components.

F11 Chat History Management

Sessions persist as JSON files. Users can create, rename, delete, and switch between sessions. Each session stores chat messages, agent messages, agent context, and timestamps.

Session Data Model

@dataclass
class Session:
    session_id: str                     # 12-char random ID
    title: str                          # extracted from first user message
    created_at: str                     # ISO timestamp, preserved on updates
    updated_at: str                     # ISO timestamp, refreshed on save
    chat_messages: list[dict]           # UI-facing conversation
    agent_messages: list[dict]          # LLM API messages (with tool calls)
    agent_context: dict = field(...)    # session memory (F3)

History Dropdown

The sidebar dropdown shows sessions sorted by updated_at (newest first). Each entry includes the timestamp, title, and message count (e.g., "2026-09-12 14:30 Create MySQL pipeline (5 msgs)"). Selecting a session restores both the chat view and the agent's internal state for seamless multi-turn continuation.
